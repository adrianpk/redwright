## Answers

### Q1. Minimum Viable Ticket Execution Scope

Question: For a rough but useful first version, what is the minimum acceptable success for the agent: completing a full programming ticket through `ready for review`, or executing a smaller slice such as preparing the sandboxed environment, attempting implementation, and reporting the result without moving the ticket yet?

Answer: Start small. The first target should be a simple ticket in an already established project. The goal is not to test huge tasks, but to validate the loop that can later become a fuller iterative loop. Once the foundations make this real, larger capabilities should follow naturally with additional work.

### Q2. Archetypal First Ticket

Question: For that first simple ticket, what kind of task should be the ideal case: documentation change, small bug with an existing test, minimal feature with a new test, lint or compile correction, or another concrete category?

Answer: The archetypal case should be a CLI-based todo list application, likely using `urfave/cli`. "Archetypal" means the general classic trivial example that follows hello world, not a RedWright-specific archetype. The ticket should implement a simple feature that closes or checks off a task, such as marking a task as done. For reproducibility, the workflow should ideally generate a test or test suite that later enables a more realistic manual verification.

### Q3. Ticket Body Contract

Question: For the agent to solve that archetypal ticket, what minimum information should be written in the ticket body: functional description, expected commands, acceptance criteria, expected test, suggested files, or should the ticket be deliberately more natural and leave part of the work for the agent to infer?

Answer: Start with a benign case: a well-specified ticket. More complicated cases, such as poorly specified tickets, can be tested later. In that later phase, after repeated unsuccessful iterations, the agent may exit the loop by leaving a ticket comment and sending a notification. One of the two main focuses of this iteration is that the agent can send the appropriate context to generate the new symbols or files required to complete the implementation correctly.

Follow-up clarification: The first main focus is that the agent can obtain its sandboxed environment and operate inside it without friction.

### Q5. Minimum Sandboxed Setup

Question: For that first version, should the sandboxed environment be dynamically generated by RedWright for the project, or is it enough for the project to already have an existing container or workspace configuration that the agent can consume and validate?

Answer: The first version can start with a setup that basically reduces to a Dockerfile. That Dockerfile may be manually generated, provided directly, or even supplied as a text file. The agent should use that specific file for a specific stack and dependency set. A later iteration can solve how to infer and generate this container setup automatically. The agent should eventually point to the formalized version of that setup. In a sense, generating the setup itself is a more complex case of solving a ticket.

### Q6. Formal Sandbox Reference Location

Question: In that first version with a provided Dockerfile, where should the Dockerfile be formally referenced so the agent can find it: in the RedWright project model, in a repository ops artifact, in the ticket, or directly through a path convention inside the workspace?

Answer: RedWright could reserve an operational area inside the project itself, eventually a `./rw` directory, where it can internally generate a convenient directory structure. The Dockerfile used by the agent for its operations is not necessarily the same Dockerfile the project requires to run in production. In this context, "not necessarily" effectively means it will not be the same.

### Q7. Purpose Of `./rw`

Question: For the first version, what should the `./rw` directory contain at minimum: only the agent's operational Dockerfile, or also metadata such as image name, test/lint/build commands, required variables, and protocol notes?

Answer: The `./rw` directory fills a gap: it can provide context that should later come directly from the platform itself. Even later, keeping such a file or directory may still be convenient because it avoids polluting the project with RedWright-specific concerns. This directory could eventually be git-ignored.

### Q8. Versioning Of `./rw`

Question: For this first version, should `./rw` be part of the project repository and versioned, or should it be a local/transient git-ignored directory that RedWright materializes when preparing agent work?

Answer: This is a repo operator decision. In the test exercise, the operator is the user. It is not central to the implementation because the project itself is created under `_workspace`, which is entirely outside RedWright's own project versioning. For now, `./rw` should be created when the project is initialized and should not be included in the generated project's `.gitignore`. The generated project should also receive a generated `.gitignore`. That said, the logic of what is versioned or not is an irrelevant detail for this implementation.

### Q9. Operational Commands

Question: For the archetypal Go CLI ticket, should the agent discover test and build commands by inspecting the repository, or should they be explicit in `./rw` or in the ticket for the first version?

Answer: There is not much to specify here. Use standard Go practices and avoid dependencies.

### Q10. Dependency Policy For The Exercise

Question: For the CLI example, you previously mentioned `urfave/cli`, but then said to avoid dependencies. Should the first test use only the Go standard library, leaving `urfave/cli` out to reduce noise?

Answer: Yes. The contradiction was noticed immediately after sending the previous answer. The original intent was to avoid testing libraries outside the standard library. That said, if command and flag parsing is trivial, RedWright can also avoid the CLI dependency for this exercise. The corrective decision is to depend only on the Go standard library for the whole exercise.

### Q11. Test Project Shape

Question: Should the Go test project already exist before the agent runs, with an incomplete implementation and a ticket asking the agent to complete it, or should RedWright also create that fixture project as part of the same test flow?

Answer: The project should be arranged to support a reliable automated workflow test. Manual failed tests can introduce noise into the exercise, so the workflow should have a strong set of table-driven tests. It may depend on LLMs, but a rich fuzzy fake with varied possible responses would be better for automated workflow validation. The goal is to test the workflow automatically with realistic variation.

Clarification before Q12: Once the test is established, the user will provide a rich set of LLM-based responses delivered with randomness by the fuzzy or table-driven test.

### Q12. Fixture Versus Workspace Project

Question: For that automated test, should the Go todo-list project be a controlled fixture inside RedWright's test suite, or a real project created under `_workspace` through the normal project creation flow?

Answer: It should use `_workspace`. In development mode, `_workspace` should include a resettable and teardown-capable space after the run. This may already exist.

### Q13. Workflow Test Assertions

Question: Should the first automated test validate only that the agent produces correct changes in the workspace, or should it also validate RedWright states such as ticket assignment, execution started, comment or error creation, commit creation, and ticket column transition?

Answer: The agent must produce a solution that resolves the ticket with no lint errors, no compile errors, and correct behavior. Ticket comments can be left out of the first iteration. However, it should not be complex for the agent to move the ticket to the review column if linting, compiling, and behavioral validation all pass appropriately.

### Q14. Commit Requirement

Question: In the first iteration, should the agent create a real commit inside the workspace when validation passes, or is it enough to leave the diff applied and move the ticket to review?

Answer: A commit is sufficient. Unless it adds disproportionate complexity, the ticket should only be sent to review after a push, but this requirement can be temporarily disabled for the test. If the fake or mock for push is trivial, it can remain part of the flow.

### Q15. Remote Git Scope

Question: For the initial test, does the workspace need a real Git remote, or is a local repository enough if the agent can create commits and RedWright can inspect them?

Answer: RedWright should simulate locally whenever possible. Making a test depend on a remote service sounds like a design smell.

### Q16. Iteration Limit

Question: In the first workflow, when lint, compile, or test errors appear, how many iterations should the agent attempt before declaring a blocker: a fixed low number, a time budget, or until the fake or LLM stops producing useful changes?

Answer: RedWright can be generous at first, but this should just be a constant in the appropriate place. The exact detail should be handled during slicing.

### Q17. Unrecoverable Error Outcome

Question: In this first version, if the agent exhausts iterations or finds an error it cannot resolve, what should the minimum result be: leave the ticket in its current column, mark it as blocked, or only record the failure in runtime/test output without touching the Kanban board?

Answer: Mark it as blocked. Ticket comments and notifications can be added later.

### Q18. Kanban State Scope

Question: For this first version, what minimum Kanban columns or states are needed to support the loop: `todo`, `in_progress`, `blocked`, `ready_for_review`, or should RedWright map to existing states even if they have different names?

Answer: This is already defined. The Kanban can go through fine-tuning later, but it is outside the scope of this exchange.

### Q19. Initial Ticket Assignment Policy

Question: For the first test, should the ticket be explicitly assigned to the coder agent before the loop starts, or can the loop take any ticket available for development?

Answer: Start with the most liberal case. It is enough that the ticket is not self-assigned to the user/admin who creates tickets. Later, RedWright can, and should, define ticket-picking logic. Tags such as priority, severity, and similar metadata already exist or are expected. Eventually rules may be more or less complex, such as choosing high-priority UI tickets.

### Q20. Loop Invocation

Question: For the first implementation, should the loop be invoked explicitly by a user or test action, like "run agent once", or should it behave like an always-on worker that automatically detects tickets?

Answer: The preferred initial manual invocation is through Telegram: a command to start the loop and a command to pause or stop it. What is not set in stone is the command name and parameterization. Later command flags, arguments, or options may tune behavior such as priorities, severities, ticket types, agent types, replicas, and similar dimensions. For now, something that starts and stops the loop is enough. This applies to manual testing. Automated tests should trigger the behavior through a command in the DDD sense.

### Q21. Loop Granularity

Question: For this first version, when the loop starts, should it process only one ticket and stop automatically, or should it keep taking available tickets until the user pauses or stops it?

Answer: Yes and no. Yes, because the initial test will basically be based on a single ticket. No, because RedWright may activate actual loop functionality. This question reveals another important mode: the initial idea was not only that the agent can process tickets in a loop, but also that the user can indicate a specific ticket and have the agent work only on that ticket. This specific-ticket mode should be considered part of the implementation.

### Q22. Specific Ticket Override

Question: When the user indicates a specific ticket through Telegram, should the agent ignore normal picking rules and work that ticket even if it is not next by priority, as long as it is not self-assigned to the user/admin?

Answer: Yes.

### Q23. Pause And Stop Semantics

Question: For the pause or stop command, is the initial acceptable behavior "do not take new tickets, but finish the current ticket", even if that takes several iterations?

Answer: Yes. This is the cleanest approach. Assume this will remain the behavior for a long time; there may never be a `SIGKILL`-style abrupt stop mode.

### Q24. Loop State Persistence

Question: Should the "stop requested / do not take new tickets" state be persisted in the database so it survives restarts, or can it be transient runtime state in the first version?

Answer: This needs more thought. Initially, the agent or agents should not be able to auto-start their loop after a restart. Later, that may probably be ideal.

### Q25. Indispensable LLM Context Sources

Question: For the first simple ticket, which context sources are indispensable for the agent to send to the LLM: ticket body, repository tree, full relevant files, existing tests, `./rw` Dockerfile, `AGENTS.md`-like protocols, or something else?

Answer: All of them. Frankly, this should be a solved topic in this cycle.

### Q26. File Context Selection

Question: To avoid sending too much context, does the first version need intelligent relevant-file selection, or can it start with a simple rule for small projects: complete tree plus complete source and test files within a reasonable limit?

Answer: As long as the payload allows it, and there should not be a problem in this case, prefer sending everything even at the cost of suboptimization. A second, near-term iteration can specifically engineer the optimization strategy.

### Q27. Previous Interaction Context

Question: For this first simple-ticket test, should previous conversational context already be included, even as transient raw or summary context, or can it be omitted because the ticket is well specified and the loop starts from zero?

Answer: Do not leave it out. Previous context adds nuance and can include strong points in the ticket resolution. The agent cannot realistically solve the ticket without a thinking process, and this requires reinforcement requests with expanded context from errors, warnings, and similar signals. In this case, previous conversation clearly means the conversation the agent has with the LLM; the human is outside the loop. Without at least recent previous context, many nuances must be formally re-expressed to reach an optimal solution.

### Q28. Previous Interaction Format

Question: For that recent agent-LLM conversation, should the first version store and inject complete raw messages, a rolling summary, or both raw recent messages and a compact accumulated summary?

Answer: Start with a raw version, or at least a considerable tail of the previous conversation. Later iterations can work on densifying previous context and sending compact, relevant data.

### Q29. Previous Interaction Storage

Question: Should that raw tail of the agent-LLM conversation be stored under `tmp/redwright/context/...` as described by the earlier draft, or in the `_workspace` project area alongside the ticket environment?

Answer: The dump associated with this quiz already includes references for handling previous conversational context. This quiz should rely on those existing references instead of redefining the storage model here.

### Q30. LLM Output Contract

Question: For the agent to apply changes without ambiguity, should the LLM respond with a structured format of operations, files, and commands, or is an explanatory text response enough for the agent to interpret?

Answer: RedWright already has a formalized semantics for LLM responses. Resolving a ticket may require revisiting this schema because new request fields may be required or helpful. Similarly, the response may also require new fields, such as arguments, post-action sets, and related execution directives.

### Q31. Change Application Responsibility

Question: In this first version, who applies concrete code changes: the agent itself executing tools or patches based on the LLM response, or should the LLM return directly applicable patches that RedWright applies deterministically?

Answer: This is a complex scope, and it is closely related to the previous question. The idea is that the harness layer, the same layer that was used in the temporarily abandoned TUI work, should operate through the minimum possible primitives. With a rich, semantically organized LLM response that induces the model to return a solution based on available commands, code, text, and affected files, the agent should be able to resolve the implementation.

### Q32. Primitive Extension Scope

Question: For this ticket execution cycle, should the agent be limited to existing primitives such as read, search, run, write, apply_patch, and git_commit, or can the spec add one or two new primitives if the loop requires them?

Answer: Without rereading the relevant drafts, specs, or code, the intended direction is not to extend those primitives. There is a possible future capability to add skills to the harness, but that is outside this scope. Even then, those skills would be convenient groupings of actions based on the same underlying primitives.

### Q33. Execution Safety Boundary

Question: In the first cycle, is the main safety restriction simply that all mutating primitives operate only inside the ticket sandbox or worktree, or do you also need explicit policies to block dangerous commands inside the container?

Answer: Dangerous commands should not be able, or at least should not be expected, to affect the host that administers the containers. The relevant danger is more about the repository itself. In that case, safety should come from a robust permission model at the remote level, such as not operating on `main`, using scoped PAM tokens, and similar controls. The blast radius should be easily contained outside RedWright.

### Q34. Branch Strategy

Question: For the first version with a local commit, should the agent always create a new branch per ticket inside the workspace, or can it work on the current branch of the project fixture?

Answer: Start with a specific branch. RedWright will probably keep this scheme later.

### Q35. Branch Naming

Question: Should the specific branch follow a simple convention such as `rw/ticket-<id>-<slug>`, or should it reuse existing repository or protocol conventions if they are already defined?

Answer: Branch naming should be defined by Protocols, another RedWright artifact. The example should not imply a default `rw/` prefix. RedWright should not self-promote or try to mark authorship in commit messages, branches, or similar surfaces. The produced code belongs to the user; RedWright is a tool.

### Q36. Commit Message Protocol

Question: For the agent's commit, should it strictly follow the project's protocol even when the ticket is a test case, for example conventional commits if the protocol says so?

Answer: Yes. This is part of validating that project context operates correctly.

### Q37. Protocol Context Source

Question: For the first test, should Protocols be materialized as files such as `AGENTS.md` inside the workspace, or is it enough for RedWright to pass them to the LLM from the Rails model?

Answer: Protocols are materialized, or at least they should be materialized by the external project materialization phase. Nothing prevents the controller that handles the scope from including them as additional file-based scope. However, if protocols also exist in model or persistence form, RedWright should eventually avoid duplicating the same information in the LLM context. The formal path should be through that layer, handled by `LLMRequestEngine`. Sending files as well would be redundant, and at some point should likely be filtered from the information sent to the LLM.

### Q38. Temporary Protocol Context Duplication

Question: In this first iteration, can RedWright temporarily accept duplicated protocol context if it arrives both through files and through the model, or should the spec require minimal deduplication from the beginning?

Answer: Yes, temporary duplication is acceptable. It should be easily detectable in `LLMRequestEngine` traces, which will certainly be scrutinized.

### Q39. Trace Scope

Question: To evaluate this first iteration, what minimum trace should be recorded for each agent attempt: context sent, LLM response, commands executed, test results, generated diff, commit hash, and ticket transition?

Answer: The previous answer was too narrow. LLM request and response interactions are already resolved through a rolling file. The broader trace question is valid: anything that enables optimal debugging by inspecting logs is welcome, even if some of it lives at debug level.

### Q40. Validation Error Context

Question: When tests, lint, or compile commands fail, should the next LLM request include full command output, or a normalized or summarized error version plus relevant files?

Answer: Yes. In a first iteration, it is acceptable for everything to go together in one property. A near-term corrective ticket can later separate different error and warning types such as linting, compile, and runtime. However, if this can be resolved clearly in the current phase, there is no resistance to doing it now.

### Q41. Manual Acceptance With Real Flow

Question: For the first implementation cycle, should acceptance require passing with a deterministic or rich fake LLM, or should there also be a manual test with a real LLM before considering the cycle closed?

Answer: The user wants to pass through a manual phase: trigger the flow from Telegram and, with a Kanban tab open, see the ticket move to review.

### Q42. Telegram Feedback During Manual Run

Question: During that manual test, besides seeing the ticket move in Kanban, should Telegram report only start and final status, or also intermediate progress such as "sandbox ready", "tests failed, retrying", and "commit created"?

Answer: A manually triggered action scoped to a ticket should always be accompanied by a final response. RedWright should not show a typing indicator for minutes. It should send an initial acknowledgement, using a typing indicator if needed, then assume asynchronous operation and send a final confirmation.

### Q43. Intermediate Progress Persistence

Question: Should the first version persist intermediate progress visibly in the ticket or runtime logs even if Telegram only receives the initial acknowledgement and final confirmation?

Answer: This is not necessary now. A ticket checklist system is a planned feature, and the agent will eventually be able to mark intermediate progress there.

### Q44. Blocked Ticket Final Message

Question: If the agent marks a ticket as blocked in this first version, should the final Telegram confirmation include the summarized technical reason even if there are not yet ticket comments or notifications?

Answer: Yes, as much as possible.
