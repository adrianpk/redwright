## Summary

RedWright needs a reusable sandbox behavior layer for agent work. The layer should not be tied to a specific agent backend, model provider, project stack, or ticket implementation strategy.

The purpose is to let RedWright prepare isolated task workspaces, run project commands through controlled execution environments, collect results, and hand those results back to the RedWright orchestration layer.

This is not a production deployment model and not a human development environment model. It is an operational behavior for agent task execution.

## Core Behavior

RedWright should support the following reusable behavior:

- prepare a task-scoped workspace
- choose an execution environment
- start that execution environment
- run commands with bounded permissions
- capture stdout, stderr, exit status, and relevant events
- collect changed files, diffs, logs, and artifacts
- close or preserve the workspace according to policy
- hand the result back to RedWright for ticket state changes and promotion decisions

This behavior should be available to more than one task execution backend.

## Layering Intent

The sandbox behavior should live below ticket execution and beside workspace preparation.

It should not know RedWright ticket semantics beyond the run metadata needed for traceability. It should not decide whether a ticket is complete, whether a result should be committed, or whether a board card should move.

Those decisions belong to higher-level orchestration and finalization layers.

The intended separation is:

```text
Task orchestration
  owns ticket lifecycle, backend selection, and kanban movement

Task workspace
  owns scratch checkout or worktree preparation

Execution environment
  owns controlled command execution

Result finalization
  owns diff inspection, validation interpretation, commit, push, and review state
```

## Workspace Model

The default model should avoid mutating the canonical project workspace directly.

Preferred behavior:

- create a ticket-scoped scratch checkout, worktree, or equivalent task workspace
- run agent work against that workspace
- preserve the canonical workspace until RedWright explicitly promotes a result
- keep enough metadata to correlate the scratch workspace with the project, ticket, backend, and run

The execution environment may need a mount point, but that mount should point to the task workspace, not blindly to the canonical project checkout.

## Execution Environment Model

The execution environment boundary should support multiple implementations behind the same behavior.

Initial environment kinds may include:

- local shell, mainly for compatibility and fallback
- Docker-based command execution
- Podman-based command execution

Future environment kinds may use explicit sync-in and sync-out instead of host-mounted workspaces.

The behavior contract matters more than the environment implementation.

## Mount and Sync Semantics

RedWright should model filesystem access explicitly.

Useful filesystem roles:

- task workspace: read/write project checkout for the current task
- context input: read-only context generated by RedWright
- output artifacts: read/write result directory for logs, diffs, reports, and structured outcomes
- caches: optional project-local or toolchain-specific caches

Environment implementations can satisfy these roles differently:

- mounted workspace environments can bind the task workspace into the runtime
- isolated environments can copy or sync the task workspace into and out of the runtime

Higher layers should not depend on which strategy is used.

## Agent Backend Relationship

The sandbox behavior is not the same as the agent backend.

Agent backends decide how work is attempted. For example:

- a managed-agent backend can run a full external coding-agent loop
- a native RedWright backend can use `LLMRequestEngine`, context policies, and RedWright's own retry loop

Both should satisfy the same RedWright task-run contract, even if their internal execution topology differs.

Interchangeability exists at the RedWright orchestration boundary, not inside the backend implementation.

This allows RedWright to build the orchestration path once and plug in different task-solving backends later.

## Configurable Ticket Execution Backends

RedWright should choose the ticket execution backend through configuration.

The first version can use static configuration. A later version can expose dynamic project-level, board-level, ticket-level, or command-level selection.

Conceptual shape:

```yaml
agent_execution:
  ticket_backend: codex_managed_worker
```

Supported backend direction:

```text
codex_managed_worker
  managed execution environment with Codex available

native_managed_worker
  managed execution environment with RedWright's native agent engine available
```

Ticket execution flow:

```text
ticket start
  -> RedWright reads backend configuration
  -> RedWright creates a task run
  -> RedWright starts the execution environment
  -> the selected worker prepares or receives the task workspace
  -> the selected worker creates a working branch or equivalent isolation
  -> the selected worker attempts the ticket
  -> the selected worker returns task result, events, diff, and validation
  -> RedWright finalizes according to policy
```

The managed worker may clone the repository or work from a prepared scratch checkout. The key requirement is that ticket work is isolated from the canonical project workspace until RedWright promotes the result.

## Host Intelligence Versus Managed Worker Execution

RedWright should not use the sandbox layer for every interaction.

Simple consultation tasks can stay in the RedWright host process:

```text
user question
  -> RedWright host
  -> LLMRequestEngine / context policy / memory
  -> answer
```

These tasks do not need a scratch workspace, project command execution, managed worker startup, or ticket lifecycle.

Code-changing tickets and task execution are different:

```text
ticket or task
  -> RedWright orchestration
  -> task workspace
  -> selected backend
  -> execution environment when needed
  -> result capture
  -> RedWright finalization
```

The native RedWright path should be modeled as a reusable agent engine, not only as ticket-specific code.

That engine can have two modes:

```text
embedded mode
  runs inside the RedWright host process for lightweight work

managed worker mode
  runs inside the execution environment for sandboxed ticket work
```

The same native engine can support non-ticket tasks and ticket execution without forcing every task into a container.

The native RedWright ticket backend can evolve in two stages.

First, RedWright can keep intelligence on the host and use the execution environment only for project commands:

```text
RedWright host:
  LLMRequestEngine
  context shaping
  command preprocessing
  retry loop
  patch decisions

Execution environment:
  dependency install
  tests
  linters
  builds
  validation commands
```

Later, RedWright may package the native engine as a smaller managed worker that runs inside the execution environment:

```text
RedWright host:
  ticket state
  project registry
  backend selection
  kanban movement
  result finalization

RedWright native agent engine:
  task packet input
  LLMRequestEngine
  command preprocessing
  patch loop
  task result output
```

That managed worker should not become a second full Rails application. It should not own the database, kanban state, project registry, or final promotion.

This creates a compatible shape for both managed-agent and native RedWright execution:

```text
task packet in
  -> backend-specific work
  -> task result, events, diff, and validation out
```

The Codex managed worker can validate the orchestration path earlier. The native RedWright engine can later plug into the same task-run contract, either embedded in the host for lightweight tasks or packaged as a managed worker for sandboxed ticket execution.

## Credential Boundary

Secrets should not flow into execution environments by default.

The default policy for native RedWright execution should be:

- RedWright host owns LLM provider credentials
- RedWright host owns git write credentials
- execution environments receive only explicitly allowed environment variables
- project secrets require an explicit allowlist and purpose

Managed-agent execution may require a different credential boundary. If the managed agent process runs inside the execution environment, then the backend may need a narrow credential injection path for that agent. That injection should be explicit, backend-specific, auditable, and separate from general project environment inheritance.

This keeps command execution isolated without turning each environment into a full RedWright runtime by default, while still allowing a managed-agent backend to run inside the sandbox when explicitly selected.

## Non-Goals

This draft does not define:

- a production Dockerfile format
- a human development container format
- the final Ruby class names
- a specific Docker or Podman command builder
- a Codex integration contract
- native RedWright LLM context policy
- git push or pull request policy
- UI controls

## Open Questions

- Should task workspaces be git worktrees, fresh clones, or both depending on project source?
- What metadata should identify a task run across workspace, execution environment, ticket, and backend?
- Should local shell execution remain available after sandboxed execution exists?
- What is the minimum result artifact contract needed by ticket finalization?
- Which secrets, if any, should be allowed into execution environments for dependency installation or integration tests?
- Should environment setup be validated during project setup, first ticket execution, or both?
