# RedWright Document Canvas and Ticket Reference Model

## Status
Draft

## Conversation
- `2026-05-01-redwright-document-canvas-and-ticket-reference-model-conv.md`

## Scope
- Define a document model centered on `draft`, `spec`, and `plan+tracking`.
- Keep tickets as the only task execution trigger while allowing rich references to longer artifacts.
- Clarify first-phase boundaries for UI and operational behavior.

## Source Context
- Current application interface is focused on ticket handling.
- Operational needs require more expressive artifacts than ticket text alone.
- The workflow should preserve rough thinking in drafts and promote curated outcomes into formal specs.

## Working Notes

### 1) Document Types and Roles
- provisional_status: `keep`
- current issue:
  - Ticket content is too constrained for large, structured task definitions.
- desired behavior:
  - Support three document types:
    - `draft`: exploratory, editable, may contain rough structure.
    - `spec`: formal, curated, stable reference.
    - `plan+tracking`: execution/readout artifact generated by the agent.

### 2) Draft to Spec Promotion
- provisional_status: `keep`
- current issue:
  - Early decisions and rationale can be lost when moving directly to formal specification.
- desired behavior:
  - Promote from `draft` to `spec` while retaining the precursor draft.
  - Keep a shared base format, with stricter curation standards for `spec`.

### 3) Plan+Tracking Ownership and Visibility
- provisional_status: `keep`
- current issue:
  - Users need comfortable visual access without depending on chat transport.
- desired behavior:
  - Agent owns creation/management of `plan+tracking`.
  - UI provides view-oriented access for reading and navigation.

### 4) Ticket as Execution Unit with References
- provisional_status: `keep`
- current issue:
  - Tickets are overloaded when they must contain full specification details.
- desired behavior:
  - Keep ticket as the only execution trigger.
  - Allow tickets to reference `spec` and, when relevant, `plan+tracking`.

### 5) Conversational Path (Future Mention)
- provisional_status: `unsure`
- current issue:
  - There is value in deriving curated artifacts from iterative conversation.
- desired behavior:
  - Mention a future conversational path where discussion can produce `draft` or directly `spec`, then flow into `plan+tracking`.
  - Treat this as out of scope for first phase implementation.

## Open Questions
- Which minimum CRUD operations are required per document type in phase one?
- Should `plan+tracking` be fully read-only in UI, or allow limited annotations?
- What metadata is required to enforce explicit draft/spec lineage?
- What permission model is needed for ticket-to-document linking?

## Out of Scope
- Full in-app conversational editing loop with LLM assistance.
- Autonomous ticket creation and self-assignment behavior by agents.
- Replacement of ticket as the canonical execution trigger.

## Next Iteration Inputs
- Define phase-one UI screens for browsing and reading document types.
- Define storage schema and lifecycle states for `draft` and `spec`.
- Define reference model between tickets, specs, and plans.
