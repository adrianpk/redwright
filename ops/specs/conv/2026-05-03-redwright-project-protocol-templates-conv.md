## Sessions

### Session 2026-05-03

#### Context

- Runtime Containers was promoted into a formal spec and implementation cycle.
- Protocols remained as a draft and still needed clarification before formal spec work.
- The user explained that RedWright already uses `AGENTS.md` and referenced files under `.agents/` as the practical shape of project protocols in this repository.
- The user also clarified that protocol information should be available both inside RedWright and to external agent tools that clone and operate on repositories directly.

#### Questions Raised

- Is `Protocol` one document or a family of project-level operational documents?
- Should Rails or filesystem files be the source of truth for project protocols?
- Should `/project new` always create a Project Protocol, even when stack-specific templates do not exist?
- How should the system behave for unsupported or unknown stacks such as Zig?
- Should a protocol generated during initialization be treated as lower-status than one sourced from templates?
- How should LLM context avoid duplicating the same protocol information from both Rails persistence and filesystem materialization?
- Should the first Protocols UI resemble filesystem documents or a more abstract composed editor?
- Should `AGENTS.md` remain the required protocol root?
- Should links between protocol files be user-authored or generated by materialization?
- Should the first version use a fixed protocol file skeleton or allow the file set to vary heavily per project?
- Should setup create protocol proposals for review, or directly create editable active project protocols?

#### Candidate Answers

- Treat `Protocol` as the project-level operational instruction set, but allow it to be represented by multiple protocol documents rather than one monolithic text blob.
- Start by replicating the protocol file shape already used successfully in this repository and related projects, even if that shape is not necessarily the final ideal design.
- Keep Rails persistence as the product source of truth.
- Materialize protocol files into `AGENTS.md` and `.agents/*.md` for interoperability with Codex or other agent tools.
- Always create a Project Protocol during `/project new`.
- Use common behavior templates by default, apply stack templates when available, and synthesize a minimal stack-aware project protocol with LLM help when no stack template exists.
- Allow project protocols to compose multiple stack-oriented overlays when the real project shape requires it, such as framework plus language plus supporting subsystems.
- Record provenance showing whether a project protocol came from common templates, stack templates, composition, initialization-time generation, or later manual authoring.
- Record provenance at the protocol-document level rather than only at the aggregate project-protocol level.
- Avoid sending duplicate protocol context to LLM requests when the same information is already attached from enriched Rails context.
- Mirror the familiar repository protocol shape in the first Rails UI to minimize operational friction.
- Keep `AGENTS.md` as the mandatory root document and derive references to other protocol files automatically during filesystem materialization.
- Keep `AGENTS.md` relatively light and structurally uniform across projects, using it as a root entrypoint that points toward more detailed protocol files.
- Use the same fixed protocol file skeleton for all projects in the first version, while varying content according to common behavior rules, stack context, and project-specific generation.
- Treat some files as behavior-oriented by nature and others as stack-oriented by nature, while still preserving the same file set across projects.
- Reflect the common-versus-stack distinction in the Rails-side model rather than relying only on ad hoc inference from filesystem documents.
- Materialize the baseline playbook set by default instead of trying to infer which playbooks are necessary per project.
- Keep the baseline playbook set itself stable across projects in the first phase rather than varying which common playbooks exist per stack.
- Create the initial Project Protocol directly during setup and let the user edit it afterward, rather than introducing a separate proposal-approval step.
- Edit Project Protocols as Markdown documents in the first phase rather than through structured form fields or semantic block editors.
- Materialize filesystem protocol files automatically when Rails-backed Project Protocols change, rather than exposing sync as a user-facing step.
- Keep stack templates as practical guidance for agents rather than as an attempt to encode an exhaustive taxonomy of technologies.
- Keep the first Protocols UX intentionally opinionated and low-configuration rather than exposing internal provenance and composition controls.
- Do not add a lightweight review-status layer to the initial Project Protocol UX; the first version should stay simple and ergonomic after setup completes.
- Do not expose an explicit `regenerate protocol` action in the first user-facing Protocols UX.
- Treat Protocols in the first iteration as strong operating guidance for compatible agents rather than as a hard execution gate equivalent to Runtime Containers readiness.
- Do not introduce hook-based protocol enforcement in this iteration.
- Treat the first-phase sync contract as one-way from Rails to filesystem rather than bidirectional.
- Keep `Documents` and `Protocols` as distinct product areas because they serve different purposes.

#### Current Convergences

- `Protocol` is a useful umbrella term even if the exact naming might still improve later.
- The practical project shape already looks like a protocol family: `AGENTS.md` as entrypoint plus referenced `.agents/*.md` files.
- Rails should be the explicit source of truth when a project is managed inside RedWright.
- Filesystem protocol files are still valuable and should exist for external tool interoperability.
- `/project new` should always create an initial Project Protocol.
- The first Protocols UI should stay close to the current filesystem metaphor, with cards or units corresponding to familiar protocol files.
- The first user-facing Protocols area should focus on concrete Project Protocols rather than on exposing separate CRUD surfaces for common and stack templates.
- Separate CRUD for common and stack templates is not part of the first project-facing surface, but it should remain near-term follow-up work rather than a distant backlog item.
- `AGENTS.md` should always exist and should remain the first/root protocol document.
- Users should not have to manually manage markdown links between protocol files in Rails.
- The projection layer should generate canonical references, including `PLAYBOOKS.md` as an index to playbooks.
- `PLAYBOOKS.md` and concrete playbook files are valuable not only as structure, but also because they let users and agents reference exactly the needed operational file without sending the entire protocol tree every time.
- Most protocol variation should live in `.agents/*` rather than overloading `AGENTS.md`.
- File-level addressability is part of the design value: sometimes the right instruction is "read `AGENTS.md` only", sometimes "read `AGENTS.md` plus references", and sometimes "read this one specific playbook."
- The first version should always materialize the same protocol file set, rather than varying the list of files heavily by project.
- The fixed file set should still allow behavior-driven versus stack-driven content to land in the naturally appropriate files, such as `ARCHITECTURE` and `CONVENTIONS`.
- The filesystem shape may make the distinction intuitive, but Rails should still carry a proper modeled counterpart for that distinction.
- Even if template administration is deferred from the first UX, the system still needs seeded reference stack templates for initial setup behavior.
- Trying to decide per-project playbook necessity up front is not worth the ambiguity cost in the first phase; a complete baseline is preferable to inconsistent omission.
- Regularity, predictability, and homogeneity are preferred over per-stack variation in the baseline playbook set, especially while the platform is still young.
- The initial seeded stack list should reflect the technologies actually used by the core development team rather than pretending to be an exhaustive or industry-neutral catalog.
- Markdown is the preferred editing format because it is semantically legible to both humans and LLMs.
- Absence of a stack template must not result in "no protocol."
- For unknown stacks, a generated minimal protocol is preferable to empty or missing files.
- Initialization-time generation should be reflected in provenance, not automatically downgraded in operational status.
- Provenance should be document-based because the protocol model itself is document-oriented.
- Initialization should create usable project protocols directly; later fine-tuning in the web CRUD is preferred over a setup-time review step.
- Enriched runtime or prompt context should include protocol information, while file-picking heuristics should avoid redundant inclusion of materialized protocol files when that would duplicate Rails-backed context.
- Automatic filesystem projection reduces user friction while keeping external tools such as Codex aligned with the same project protocol state.
- Manual edits to materialized protocol files may exist for external-tool usage, but they are not canonical and may be overwritten by later Rails-side changes.
- Template selection should follow the actual combined project shape, and LLM inference may need to choose the more operationally relevant layer, such as `Rails` over generic `Ruby` where the framework dominates practical conventions.
- Provenance may be preserved internally without being surfaced prominently in the first user-facing CRUD experience.
- Protocol effectiveness is expected to rely primarily on OpenAI-style agent adherence in this iteration; Anthropic-specific hook-heavy enforcement is outside current scope.
- This is not framed as animosity toward Anthropic services, but as a practical platform constraint: their product direction appears less welcoming to harness-style systems, so this software factory should not base its primary protocol model on those assumptions in the current iteration.
- The decision to mirror the current file structure is deliberate first-phase pragmatism for familiarity and lower operational friction, not a claim that the current file topology is already optimal.
- MVP ergonomics matter more than exposing extra review states or decision branches to the user in the first iteration.
- The first Protocols implementation should automate the workflow shape already used successfully in this repository instead of inventing a new filesystem placement model.
- The seeded stack list will inevitably have noticeable omissions and uneven depth because it is grounded in the team's daily practice and actual know-how, not in a claim of broad template completeness.
- Future template CRUD should allow users to add the stacks that matter to them, including technologies that are currently omitted or only weakly covered.
- Future template CRUD should also let users adapt baseline playbooks before relying heavily on the platform, but agent operation should not depend on playbook perfection.
- `Documents` are primarily project and feature information, while `Protocols` are operational guidance for agents and LLMs.

#### Open Tensions

- Whether the project-level CRUD should expose one composed protocol view, a document list, or both.
- Whether template composition should be explicit in the first persisted model or only visible through provenance.
- How much of the filesystem materialization should be editable directly versus regenerated from Rails-managed state.
- Whether protocol usability should ever gate ticket execution the way Runtime Containers readiness does.
- How much explicit typing Rails needs per protocol file versus relying on the known canonical file set in the first version.

#### Provisional Decisions

- `keep`: Protocols are project-level operational instructions, distinct from Runtime Containers.
- `keep`: Protocols can be represented as a family of documents, not necessarily a single text entity.
- `keep`: Rails persistence is the source of truth for Project Protocols.
- `keep`: `AGENTS.md` and `.agents/*.md` are materialized projections for interoperability.
- `keep`: `/project new` always creates an initial Project Protocol.
- `keep`: the first Protocols UI should mirror the current filesystem-oriented protocol shape.
- `keep`: the first Protocols project-area UX should focus on editing the concrete Project Protocol attached to a project.
- `keep`: initial stack-template seeds should be chosen from the team's real working stacks, with no pretense of exhaustive coverage.
- `keep`: `AGENTS.md` is mandatory and acts as the canonical root of the protocol set.
- `keep`: `AGENTS.md` should stay lightweight and broadly homogeneous across projects.
- `keep`: links between protocol files are generated by the materialization layer, not manually maintained by the user.
- `keep`: `PLAYBOOKS.md` should be generated as an index over concrete playbook files.
- `keep`: playbooks should remain individually addressable files because targeted references reduce unnecessary context filler.
- `keep`: the first version should create the same protocol file skeleton for every project.
- `keep`: behavioral versus stack-specific guidance can be expressed through content allocation within that fixed skeleton rather than by changing the file list.
- `keep`: Rails should explicitly model whether protocol content is common/behavioral or stack-specific.
- `keep`: the first version should materialize the baseline playbook set for every project rather than selectively omitting playbooks.
- `keep`: the common playbook set itself should stay uniform across projects in the first phase.
- `keep`: the first editing experience should be raw Markdown per protocol document.
- `keep`: Rails-to-filesystem protocol materialization should happen automatically in the first phase.
- `keep`: first-phase protocol sync is one-way from Rails to filesystem; no re-import contract is required.
- `keep`: common behavior templates apply by default when available.
- `keep`: stack-specific templates apply when available, including multiple overlays when the project shape warrants it.
- `keep`: if no stack template exists, the system may synthesize a minimal project protocol during initialization.
- `keep`: provenance should be tracked per protocol document, not only for the project protocol as a whole.
- `keep`: provenance should distinguish template-derived, composed, initialization-generated, and manually authored protocols.
- `keep`: provenance does not need to be visible in the first Protocols UX.
- `keep`: the initial Protocols UX should not introduce non-blocking review states after setup.
- `keep`: the initial Protocols UX should not expose protocol regeneration as a separate user action.
- `keep`: Protocols are guidance-first in this iteration and should not introduce a Runtime-Containers-like hard readiness gate.
- `keep`: hook-based protocol enforcement is out of scope for this iteration.
- `keep`: initialization-generated protocols are active/editable project protocols, not merely review proposals.
- `keep`: prompt-building or context enrichment should prefer one canonical protocol source per request and avoid sending duplicated protocol content from both Rails and filesystem.
- `keep`: template coverage should stay intentionally selective; protocols are primarily there to help agents operate correctly, not to maintain a massive human-facing template catalog.
- `keep`: some seeded stacks may still have uneven quality because the team does not use all of them equally often; later CRUD should let users refine or extend that coverage.
- `keep`: the first UX should favor a GNOME-like constrained experience over a KDE-like highly configurable surface.
- `keep`: `Documents` and `Protocols` remain separate product areas even if both are rendered as Markdown collections.
- `keep`: materialized protocol files should live at the repository root and under `.agents/`, matching the current working pattern exactly.
- `defer`: exact CRUD shape and editor model.
- `defer`: separate administration surfaces for common templates and stack templates, but only as a near-term follow-up after the first Project Protocol surface exists.
- `defer`: exact template merge algorithm.
- `defer`: exact sync policy between Rails protocol state and filesystem materialization.

#### Deferred / Out of Scope

- detailed persistence schema
- exact merge algorithm for protocol templates
- direct bidirectional sync from filesystem back into Rails
- re-import of manual filesystem protocol edits into Rails-managed protocol state
- final UX language review for whether `Protocol` remains the best product term
- readiness or gating semantics for protocol quality
- Anthropic-oriented enforcement strategies such as hook-driven protocol control
